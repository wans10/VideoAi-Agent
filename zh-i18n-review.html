审查结论

与原方案的差异汇总

4 项勘误 · 2 项补充
1. 遗漏文件：routing-marketing.ts
原方案未列入此文件，但它是博客路由分发、本地化示例路径前缀检测和 dotted-model 路径兼容的核心控制器。包含 L134、L140、L151 三处硬编码 fr/es 检查。漏改将导致中文路由静默失效，表现为中文用户访问 /zh/models/xxx 时被错误路由。
2. 遗漏文件：comparison-indexation.json
compare-hub/indexation.ts 在运行时从此 JSON 读取 noindexByLocale.zh，若 JSON 中不存在 zh 键，?? [] 兜底虽可防止崩溃，但这是隐性依赖，应显式补充 "zh": []。
3. label 不一致：localeLabels.zh vs LanguageToggle defaultOptions.label
原方案 localeLabels 写 '中文'，LanguageToggle 的 label 写 '简体中文'。AppLanguageToggle 通过 Object.entries(localeLabels) 自动渲染，会显示 '中文'；营销前台手写 defaultOptions 显示 '简体中文'。两处应统一，推荐统一为 '简体中文'。
4. 类型安全盲区：if/else 链文件不受 TypeScript 保护
modelLanding.ts、GenerationPendingStatus.tsx、MarketingNav.tsx、BillingClient.tsx 使用 if/else 或朴素对象字面量，AppLocale 扩充后 TypeScript 不会报错提示遗漏。这些文件必须在实施清单中手动追踪，不能依赖编译报错引导。建议在实施时顺手将这些模式重构为 Record<AppLocale, T>。
方案正确判断：URL slug 策略
中文路径统一使用英文语义化标识（/zh/models、/zh/pricing 等）的策略完全正确，与 Stripe、OpenAI、Vercel 等产品的中文站最佳实践一致。这同时简化了 routing-marketing.ts 中 L140 的处理（zh localizedBase 等于 'models'，与 en 相同，无需特殊翻译路径）。
建议：实施顺序关键提示
Step 0（所有步骤前）：先在 locales.ts 扩充 AppLocale，让 TypeScript 立即报出所有 Record<AppLocale, T> 缺失项，用编译错误清单驱动后续工作，比人工逐文件核对更可靠。
注意：routing-marketing.ts 和 if/else 链文件不会产生编译报错，必须在 Step 2 人工检查。
